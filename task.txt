TASK: Регистрация + авторизация + доступ к секретным данным (Node.js без библиотек)

Цель
Собрать минимальный HTTP-сервер на Node.js (без сторонних библиотек), который:
- раздаёт HTML в корне (/)
- регистрирует пользователей
- авторизует пользователей и выдаёт серверную сессию через cookie
- защищает ДВЕ страницы: /data-first и /data-second через общий middleware/обёртку
- хранит пользователей в JSON-файле
- логирует каждый входящий запрос (время, URL, User-Agent)

Ограничения
- Нельзя использовать сторонние библиотеки (express, cookie-parser и т.д.).
- Разрешены только встроенные модули Node.js: http, fs, crypto, url и т.п.
- В качестве логина используем ТОЛЬКО email.

Файлы
- server.js — основной сервер
- db.json — “база” пользователей (JSON)
- (опционально) public/ — статические файлы (html/css)

База (db.json)
Структура (минимум):
{
  "users": [
    {
      "id": "random-or-uuid",
      "email": "user@example.com",
      "passwordHash": "sha256 hash"
    }
  ]
}

Требования:
- email уникален (нельзя зарегистрировать существующий email)
- пароль НЕ хранить в открытом виде — хранить только passwordHash

Хеширование паролей
Использовать встроенный crypto.
Пример:
- crypto.createHash("sha256").update(password).digest("hex")

Важно:
- Пароль не логировать и не сохранять как есть.

Сессии и cookie (серверная авторизация)
- После успешного логина сервер создаёт сессию В ПАМЯТИ:
  sid -> { userId, expiresAt }
- Клиенту в cookie отправляется только sid (не email/не флаг/не роль).
- Доступ к /data-first и /data-second проверяется ТОЛЬКО по cookie sid и серверному хранилищу сессий.

Требования к sid:
- sid должен быть криптографически случайным:
  crypto.randomBytes(24).toString("hex")

Cookie:
- Сервер выставляет Set-Cookie:
  sid=<value>; HttpOnly; SameSite=Lax; Path=/; Max-Age=3600
- Secure можно не включать для локальной разработки.

Логирование запросов
На КАЖДЫЙ запрос писать в console.log строку:
[ISO_TIME] METHOD URL UA="..."
Где:
- ISO_TIME = new Date().toISOString()
- URL = pathname (+ query по желанию)
- UA = req.headers["user-agent"] || ""

Роуты и поведение

1) GET /
Отдать HTML страницу.
Поведение:
- если пользователь авторизован (есть валидный sid в cookie и активная сессия на сервере):
  показать ссылки/кнопки на /data-first и /data-second (или сделать авто-редирект на /data-first)
- если НЕ авторизован:
  показать форму регистрации (POST /register)
  показать форму логина (POST /login)

2) POST /register
Входные данные:
- email
- password

Формат запроса: выбрать ОДИН и использовать везде:
- application/x-www-form-urlencoded (предпочтительно для HTML-форм)
или
- application/json

Валидация:
- email обязателен, строка, минимальная проверка формата (есть "@", есть точка после "@")
- password обязателен, минимум 8 символов

Логика:
- если email уже есть в db.json -> ошибка (400/409)
- иначе:
  - создать пользователя: id, email, passwordHash
  - записать в db.json

Ответ:
- успех: редирект на / (или JSON { ok: true })
- ошибка: понятное сообщение (без лишних подробностей)

3) POST /login
Входные данные:
- email
- password

Логика:
- найти пользователя по email в db.json
- сравнить sha256(password) с stored passwordHash
- при успехе:
  - создать sid и сохранить сессию в памяти с expiresAt (например сейчас + 1 час)
  - выставить cookie sid
  - редирект на /data-first (или /)
- при неуспехе:
  - одинаковая ошибка: "Неверный email или пароль"

4) Middleware / обёртка authRequired
Сделать общий механизм проверки авторизации, который ПЕРЕИСПОЛЬЗУЕТСЯ в двух ручках /data-first и /data-second.
Что делает:
- парсит cookie из заголовка Cookie (вручную)
- проверяет наличие sid и его существование в хранилище сессий
- проверяет, что expiresAt не истёк
- если ок -> вызывает защищённый обработчик
- иначе -> редирект на / (или 401)

5) GET /data-first (защищённый)
- доступ только авторизованным
- если авторизован -> вернуть HTML с секретом, например: FLAG{first_secret}
- если нет -> редирект на /

6) GET /data-second (защищённый)
- доступ только авторизованным
- если авторизован -> вернуть HTML с другим секретом: FLAG{second_secret}
- если нет -> редирект на /

7) (Рекомендуется) POST /logout
- удалить сессию по sid
- очистить cookie:
  Set-Cookie: sid=; Max-Age=0; Path=/; HttpOnly; SameSite=Lax
- редирект на /

Нефункциональные требования
- 404 на неизвестные роуты
- не печатать пароль в логах
- секреты/флаги не должны быть на странице /, только на защищённых страницах

Критерии приемки (чеклист)
- [ ] /register создаёт пользователя в db.json, email уникален
- [ ] пароль в db.json НЕ хранится открыто (только sha256-хэш)
- [ ] /login ставит cookie sid и создаёт серверную сессию
- [ ] /data-first и /data-second защищены одним общим authRequired (без копипасты проверки)
- [ ] без sid или с невалидным/просроченным sid доступ запрещён
- [ ] каждый запрос логируется: время + URL + user-agent
- [ ] не используются сторонние библиотеки
